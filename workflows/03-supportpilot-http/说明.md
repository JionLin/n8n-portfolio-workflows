# 03 SupportPilot HTTP bridge

Lets an n8n workflow send a question to a running SupportPilot backend and return the answer. The n8n side is a webhook in front of `POST /api/chat`, using the non-streaming JSON response.

Files:

- `supportpilot-http.json`: the workflow.
- `fixtures/webhook-input.example.json`: body to POST to n8n for a new conversation.
- `fixtures/webhook-input.followup.example.json`: body for a follow-up in an existing conversation.
- `fixtures/supportpilot-request.example.json`: body n8n sends to SupportPilot.
- `fixtures/supportpilot-reply.mock.json`: **placeholder**, not a recording. Only `conversation_id` is shown.

## SupportPilot API used

Schema from SupportPilot `backend/app/api/chat.py`:

```json
{ "message": "string (1..4000)", "conversation_id": "uuid | null (optional)" }
```

- `message` is required, 1 to 4000 characters.
- `conversation_id` is optional. Send `null` (or omit it) to start a conversation. To continue one, send the `conversation_id` from the previous reply.
- The response is the AgentReply JSON, which includes `conversation_id`. SSE (`Accept: text/event-stream`) is also available, but this workflow uses JSON.

## Pointing at a running SupportPilot

SupportPilot defaults to `http://127.0.0.1:8000`. Set `SUPPORTPILOT_BASE_URL` to where the backend is reachable from n8n:

| n8n runs as | Use |
| --- | --- |
| Docker Compose (this repo) | `http://host.docker.internal:8000` (the compose file maps this to the host) |
| Native process on the same machine | `http://127.0.0.1:8000` |
| Another host or container | its reachable URL, for example `http://supportpilot:8000` on a shared Docker network |

`127.0.0.1` inside the n8n container points at the container itself, not at your host. That is why the Docker value differs.

Check the backend first:

```bash
curl http://127.0.0.1:8000/api/health
```

The Manual Trigger **Health Check (manual)** in the workflow calls the same endpoint through n8n.

## Flow

1. **Ask SupportPilot Webhook** (`POST /webhook/ask-supportpilot`) receives JSON.
2. **Validate Chat Request** (Code node) trims `message` and checks:
   - `message` is not empty and is at most 4000 characters (counted by code point, as Python's `len` does);
   - `conversation_id` is absent, empty or `null`, or a UUID.
3. **Request Is Valid?** sends invalid input to **Reject Invalid Request**, which responds `400 {"error": "<code>"}`. The codes are `message_required`, `message_too_long` and `conversation_id_invalid`.
4. **POST SupportPilot /api/chat** sends `{"message": ..., "conversation_id": ...}` with a 60-second timeout.
   - Success: **Return AgentReply** responds `200` with the backend JSON unchanged, including `conversation_id`.
   - Failure (connection error, timeout, non-2xx): **Return Upstream Error** responds `502 {"error":"supportpilot_unavailable",...}`.

## Try it

New conversation:

```bash
curl -X POST http://localhost:5678/webhook/ask-supportpilot \
  -H "Content-Type: application/json" \
  -d @fixtures/webhook-input.example.json
```

Follow-up: copy `conversation_id` from the previous reply into the body, for example from `fixtures/webhook-input.followup.example.json`.

Request n8n sends to SupportPilot for a new conversation:

```json
{
  "message": "How do I reset my password?",
  "conversation_id": null
}
```

## Limits

- Only JSON responses are used. The n8n HTTP Request node reads the whole body before passing it on, so an SSE stream would arrive as one text blob. Parsing `token`, `tool_end`, `citation`, `final` and `error` events would need a Code node that splits on blank lines. Use SSE only in a client that handles it.
- The AgentReply body is passed through without reading its fields, so changes to AgentReply do not break this workflow.
- The webhook has no authentication. See the self-host guide before exposing it.

## Verification

Tested against a local stub that implements `GET /api/health` and `POST /api/chat` with the schema above:

- a valid message was forwarded with `conversation_id: null`, and the stub reply came back unchanged;
- an empty message returned 400 `message_required`;
- a malformed `conversation_id` returned 400 `conversation_id_invalid`;
- an unreachable backend returned 502.

No real SupportPilot instance was available, so the request and reply were not checked against a live backend.
